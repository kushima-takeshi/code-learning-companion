# フェーズ3の設計

> 状態: 前提見直し中。APIキーでGoサーバーからAIを呼ぶ設計を含む草案です。
> ユーザーのAIツールとの連携・開発中の自動収集は、[検討メモ](ai-tool-integration-study.md)を参照してください。構成が決まるまで本書の生成・判定APIは確定扱いにしません。

## 1. データの構成

取り込み済みのPRスナップショットを教材の正本とする。
学習データは、次の4種類に分けてPostgreSQLへ保存する。

### LearningCandidate（学習候補）

PRから生成された、学習対象の提案。

- 所有者のユーザーID
- 元になったPRスナップショットID
- タイトル
- 短い説明
- 表示の優先順位
- 優先する理由
- 根拠参照
- 作成日時

候補は最大3件をユーザーに提示する。
候補を生成しただけでは、問題セットは作成しない。

### LearningSet（問題セット）

ユーザーが選んだ1件の候補について生成する問題のまとまり。

- 所有者のユーザーID
- 選択した学習候補ID
- 状態
- 作成日時
- 学習完了日時

元のPRスナップショットは、学習候補を通じて特定する。
問題セットには2〜3問を所属させる。
状態の種類と完了条件は、状態遷移の設計で定める。

### Question（問題）

問題セットに所属する個々の問題。

- 所有者のユーザーID
- 所属する問題セットID
- 問題種別
- 問題文
- 表示用のコード断片
- 選択肢（選択肢問題のみ）
- 正解の選択肢（選択肢問題のみ）
- 判定に必要な期待要点
- 根拠参照
- セット内の出題順序
- 作成日時

問題種別は、選択肢・自由記述・コード記述の3種類とする。
正解と期待要点は、回答前の問題取得APIには含めない。

### AnswerAttempt（回答履歴）

ある問題に対する、1回分の回答とその判定結果。

- 所有者のユーザーID
- 回答した問題ID
- 回答内容
- 苦手理由（任意）
- 判定処理の状態
- 理解度（判定前は未設定）
- フィードバック（判定前は未設定）
- フィードバックの根拠参照
- 回答日時
- 判定完了日時

回答を修正して再提出した場合は、新しい回答履歴を追加する。
通信失敗などによる判定の再試行では、同じ回答履歴を使う。

判定処理の状態と理解度は分けて管理する。
通信失敗を、理解度の「判定保留」として扱わない。

## 2. データ同士の関係

- PRスナップショット1件に、複数の学習候補が関連する。
- 学習候補1件に、問題セットが関連する。
- 問題セット1件に、2〜3問が所属する。
- 問題1件に、複数の回答履歴が関連する。

候補の再生成と、同じ候補からの問題セット再作成の扱いは、
保存タイミングの設計で定める。

## 3. 共通ルール

- 各データはUUIDのIDを持つ。
- 所有者は認証済みユーザーから決定する。
- 関連付ける親データも、同じユーザーの所有物であることを保証する。
- OpenAI APIキーは、これらのデータに保存しない。
- 根拠参照の形式と検証方法は、第4節に定める。

## 4. 根拠参照

### 基本方針

問題を生成するのは、ユーザー自身のAPIキーで呼び出すAIモデルである。
アプリは保存済み教材をモデルへ渡し、生成結果を検証・保存・表示する。
モデルには問題・正解・解説とともに、根拠の場所を返してもらう。

根拠参照を保存する目的は、生成後にユーザーが問題やフィードバックの
出典を確認できるようにすることである。

根拠参照には、保存済みPRスナップショット内の場所だけを保存する。
抜粋本文（excerpt）は、根拠参照として重複保存しない。
表示時に、所有者を確認したうえで保存済み教材の指定範囲を読み出す。

問題に含める表示用コード断片（穴埋めなどの出題用コード）と、
出典を示す根拠参照は別の役割として扱う。

GitHub上の最新データではなく、取り込み時点の教材と照合する。
候補・問題・フィードバックは、それぞれ1件以上の根拠参照を持つ。

根拠参照は各データのJSONBカラムに配列として保存する。
この段階では、根拠専用のテーブルは作成しない。

### 共通項目

- kind: 根拠の種別
- snapshot_id: 根拠が属するPRスナップショットID

kindごとに、以下の位置情報を追加する。

### 根拠の種別と位置情報

#### pr_body：PR本文

- start_line: 開始行
- end_line: 終了行

#### file_content：保存済みファイル本文

- path: リポジトリ内のファイルパス
- start_line: 開始行
- end_line: 終了行

取り込み時にファイル本文を保存できた場合だけ使用する。

#### diff：保存済みの差分

- path: 差分内のファイルパス
- start_line: 保存済みdiffテキスト内の開始行
- end_line: 保存済みdiffテキスト内の終了行

行番号は、変更前・変更後のソースコードの行番号ではなく、
保存したdiffテキスト全体に対する行番号とする。
表示時に読み出す断片には、追加行の「+」や削除行の「-」も含める。

#### review_comment：レビューコメント本文

- comment_id: GitHubのレビューコメントID
- start_line: コメント本文内の開始行
- end_line: コメント本文内の終了行

#### conversation：取り込んだ会話本文

- conversation_upload_id: 保存した会話のID
- start_line: 会話本文内の開始行
- end_line: 会話本文内の終了行

### 行番号のルール

- 行番号は1から始める。
- 開始行と終了行を両方含む。
- CRLFとCRをLFへ揃えてから行を数える。
- 表示時も同じ改行の正規化を行って指定範囲を読み出す。
- 空白やインデントは削除しない。

### 保存前の検証

生成結果に含まれる根拠参照は、サーバーで検証する。

1. 対象スナップショットが認証済みユーザーの所有物である。
2. snapshot_idが、今回の生成対象スナップショットと一致する。
3. kindに必要な位置情報が揃っている。
4. 指定したファイル・コメント・会話が対象教材に存在する。
5. 行範囲が有効であり、diffの場合は指定ファイルの範囲内にある。

検証に失敗した生成結果は保存せず、構造化出力不正として扱う。
既存の候補・問題・回答履歴は削除しない。

回答を先に保存している場合は、その回答を残したまま、
判定処理を失敗として扱い、再試行できるようにする。

### 設計意図を扱う条件

差分やコードだけを根拠に、作者の設計意図を断定しない。

設計意図を問う場合は、PR本文・レビューコメント・会話に、
その判断理由を説明する記述が必要となる。

根拠の参照先と行範囲の存在・妥当性は機械的に検証する。
参照先の内容が問題や解説の内容を支えるかどうかは、
位置の検証とは別に扱う。

### APIで返す情報

根拠の表示には、種別・位置情報と、保存済み教材から読み出した断片を返す。
レスポンス用の断片は表示時に取得するもので、根拠参照には保存しない。
PR番号とhead commit SHAは、関連するスナップショットから取得する。
Object Storageの内部キーは返さない。

### サイズ制限の扱い

以前の案にあったexcerptの4 KiB上限、根拠最大3件、合計12 KiB上限は採用しない。
AIへ送る教材の入力上限と、根拠表示時の読み出し・レスポンス上限は別に設計する。
場所だけ保存することは、教材を無制限にモデルへ送信・画面へ表示してよいことを意味しない。
具体的な上限と、上限を超えた場合の表示方法は後続の設計で決める。

## 5. 保存タイミングと失敗時の扱い

### 学習候補

1. 所有者を確認し、保存済み教材を読み出す。
2. AIモデルへ候補の生成を依頼する。
3. 生成結果の形式と根拠参照を検証する。
4. 検証に通った候補を、まとめて保存する。

生成や検証に失敗した場合、その回の候補は保存しない。
既存の候補は削除しない。

有効な候補が0件の場合は、通信失敗とは区別し、
「この教材から学習候補を見つけられなかった」と表示する。

### 問題セットと問題

1. 選択した候補の所有者を確認する。
2. 候補と保存済み教材をAIモデルへ渡す。
3. 生成された2〜3問の形式と根拠参照を検証する。
4. 問題セットと全問題を、1つのDBトランザクションで保存する。

全問題を保存できた場合だけ、保存を確定する。
問題セットだけ、または一部の問題だけが残る状態にはしない。

生成や検証に失敗した場合、選択した候補は残し、
問題セットと問題は保存しない。

保存直後の問題セットの状態は、in_progress（学習中）とする。

### 回答履歴

1. 対象問題の所有者と、回答形式を検証する。
2. 回答内容と任意の苦手理由を保存する。
3. 保存済みの回答に対して判定を行う。
4. 判定結果を検証し、同じ回答履歴へ保存する。

選択肢問題は、サーバーが正解の選択肢と比較して判定する。
自由記述・コード記述問題は、AIモデルが判定する。

回答の保存に失敗した場合は、判定を開始しない。

回答の保存後に判定が失敗した場合は、回答内容を残す。
判定の再試行では新しい回答履歴を作らず、同じ回答を使う。
回答内容を修正して提出する場合は、新しい回答履歴を作る。

### 判定処理の状態

AnswerAttemptは、次の判定処理状態を持つ。

- pending: 回答保存済みで、判定結果がまだ保存されていない
- succeeded: 有効な判定結果を保存済み
- failed: 判定処理が失敗し、再試行が必要

状態の基本的な遷移は、次のとおり。

- 回答保存時: pending
- 判定成功時: pending → succeeded
- 判定失敗時: pending → failed
- 再試行時: failed → pending

サーバー停止などでpendingのまま残った回答も、復旧の対象とする。
処理中の判定と重複しない再試行方法は、API設計で定める。

### 判定処理状態と理解度の違い

理解度は、判定処理の状態とは別の項目として持つ。

- できた
- 一部できた
- もう一度
- 判定保留

pending・failedでは、理解度は未設定とする。

AIが回答と根拠を確認したうえで「判定保留」と判断し、
有効な結果を返した場合、判定処理状態はsucceededとする。

通信失敗や不正な生成結果を「判定保留」に置き換えない。

## 6. 問題セットの学習完了

### 状態

LearningSetは、次の状態を持つ。

- in_progress: 学習中
- completed: 一通りの回答と判定を完了

completedは、全問正解や知識の定着を意味しない。
知識の定着は、後続の復習機能で扱う。

### 完了条件

セット内のすべての問題が、次の条件を満たしたときに完了する。

- 判定処理がsucceededの回答履歴がある。
- その回答の理解度が、次のいずれかである。
  - できた
  - 一部できた
  - もう一度

初回の学習完了までは、各問題の最新の回答履歴を使って判定する。
古い回答が条件を満たしていても、最新の回答がpending・failed・
判定保留の場合、その問題は完了条件を満たさない。

判定保留の場合は、回答を修正して再提出できる。
通信失敗などの場合は、同じ回答の判定を再試行できる。

### 完了時の保存

最後の未完了問題が完了条件を満たしたとき、
LearningSetをin_progressからcompletedへ変更し、
学習完了日時を記録する。

回答の判定結果の保存と、問題セットの完了更新は、
1つのDBトランザクションで行う。

同じセットへの同時処理でも更新漏れが起きないよう、
完了判定に関わる更新はセット単位で直列化する。

### 完了後の回答

完了後も回答を追加できる。

追加回答によって、問題セットをin_progressへ戻さない。
学習完了日時は、初めて完了した日時を保持する。
追加回答の理解度と判定処理状態は、回答履歴として残す。

### 後続フェーズとの境界

フェーズ3では、学習完了状態と学習完了日時まで保存する。
復習予定の作成と、定着済みの判定はフェーズ4で実装する。

## 7. APIの構成

### 共通方針

- すべてのAPIでログインを必須とする。
- 所有者のユーザーIDは、認証情報から取得する。
- リクエスト本文で所有者を指定させない。
- 対象データと関連する教材が、認証済みユーザーの所有物か確認する。
- 他ユーザーのデータは、存在しない場合と同じ404を返す。
- GETは保存済みデータの取得だけを行い、AIを呼び出さない。
- AIを利用する操作は、明示的なPOSTで行う。
- OpenAI APIキーは利用するリクエストだけで受け取り、保存しない。

### 学習候補の生成

POST /pr-snapshots/{snapshot_id}/learning-candidates

指定した保存済み教材から、AIで学習候補を生成する。
検証後に保存し、候補の一覧を返す。

候補が0件の場合は、正常な結果として空の一覧を返す。
生成失敗とは区別する。

### 学習候補の取得

GET /pr-snapshots/{snapshot_id}/learning-candidates

指定した教材について、保存済みの候補一覧を返す。
候補が未生成の場合は、空の一覧を返す。

### 問題セットの生成

POST /learning-candidates/{candidate_id}/learning-sets

選択した候補について、AIで2〜3問を生成する。
検証後に問題セットと全問題を保存する。

レスポンスには、作成した問題セットのIDを返す。
画面は、そのIDを使って問題セットを取得する。

### 問題セットの取得

GET /learning-sets/{set_id}

次の情報を返す。

- 問題セットのID・状態・学習完了日時
- 選択した候補の情報
- 出題順に並べた問題
- 各問題の根拠参照

問題には、問題文・表示用コード・選択肢・出題順序を含める。
採点用の正解・期待要点は含めない。

### 回答の提出

POST /questions/{question_id}/answer-attempts

回答内容と任意の苦手理由を受け取り、回答履歴を保存する。
このAPIでは判定を実行せず、pending状態の回答履歴を返す。

保存成功後、画面が判定APIを呼び出す。
これにより、判定が失敗しても保存済み回答のIDで再試行できる。

### 回答の判定・再試行

POST /answer-attempts/{attempt_id}/evaluation

保存済みの回答を判定し、その回答履歴へ結果を保存する。

- 選択肢問題はサーバーが判定する。
- 自由記述・コード記述問題はAIが判定する。
- succeededの場合は保存済みの結果を返し、再判定しない。
- failedの場合は、同じ回答の判定を再試行する。
- pendingの場合は、未処理か実行中かを区別して扱う。

実行中の処理と再試行が重複しない仕組みは、
後続のAPI詳細設計で定める。

### 回答履歴の取得

GET /questions/{question_id}/answer-attempts

指定した問題の回答履歴を、回答日時の順で返す。

各履歴には、次の情報を含める。

- 回答履歴ID
- 回答内容・苦手理由
- 判定処理状態
- 理解度・フィードバック・根拠参照
- 回答日時・判定完了日時

まだ判定されていない項目は未設定として返す。

### 根拠本文の取得

GET /learning-candidates/{candidate_id}/evidence/{index}
GET /questions/{question_id}/evidence/{index}
GET /answer-attempts/{attempt_id}/evidence/{index}

indexは、そのデータに保存された根拠参照配列の位置とし、
0から始める。

所有者と保存済みの根拠参照を確認し、
教材から該当範囲を読み出して返す。

クライアントが任意のObject Storageキーを指定する形式にはしない。
