# AIツール連携・開発中の自動収集の検討メモ

更新日: 2026-10-23
状態: 検討中。構成・対応範囲は未決定。公式資料による調査までで、実機検証は未実施。

## 1. ユーザーが実現したい体験

対象はCursor・Claude Code・Codexなどを使い、AIの補助で開発している人。
開発の開始から終了までのコード変更や会話を取得し、実際の開発内容から学習候補・問題・解説を作り、理解と定着を支援したい。

- PRを手動で選ぶ体験だけでなく、開発セッションの継続的な自動収集を考えている。
- 問題生成、自由記述・コード回答の判定、問題と回答に即した解説はAIに任せたい。
- ユーザーが普段契約しているAIツールを活用する方向に関心がある。
- 入口は学習アプリでもAIツールでもよい。操作の少なさ・使いやすさを優先する。
- 別の収集アプリを作る案については、開発・配布・更新の負担も含めて検討したい。

「対象者にはAPIキー利用者より既存AIツールの契約者が多そう」という認識は仮説であり、ユーザー調査で確認した事実ではない。

## 2. 当初の設計と、見直しの理由

既存要件は、公開PRを指定して取り込むMVPと、OpenAI BYOKを前提としていた。
開発セッションの開始・終了と自動収集は後続機能に分けられていた。

当初の生成経路:

```text
ブラウザ → Goサーバー → ユーザーのAPIキーでOpenAIを呼ぶ
                       → 生成結果を検証・保存 → ブラウザ
```

API利用とAI製品の月額契約は同一ではない。通常のAPIキーによる利用を、ChatGPTなどの契約内で使えると説明してはいけない。
一方、公式の契約連携経路がある製品もあり、「別途APIキーが必須」と一括して決めつけることもできない。

検討途中でMCPを使い、AIのチャットから教材取得・結果保存を行う案を提示した。
ただし、MCPだけでは開発中の継続的な収集や、終了後のAI実行までは実現しない。
「チャットで学習を依頼する」だけでは、ユーザーの想定する自動収集体験を満たさない。

## 3. 分けて設計する3つの役割

| 役割 | 必要な処理 |
|---|---|
| 開発記録の収集 | 会話・コード変更・Git情報の取得、開始と終了の識別 |
| AIの実行 | 記録を渡して候補・問題・判定・解説を生成 |
| 学習サービス | 教材や履歴の保存、問題表示、復習管理、所有者確認 |

収集方法とAIの実行方法は別の選択である。
AIがアプリの機能を呼ぶMCP、イベントを通知するフック、プログラムからAIを実行するCLI等を混同しない。

## 4. 公式資料で確認した実現手段

### 開発記録の収集

| ツール | 接続口 | 制約・検証点 |
|---|---|---|
| Cursor | sessionStart/sessionEnd、編集・ツール実行のフック、transcript_path | 会話ログが無効だと本文を取得できない。対象モードごとの取得範囲を検証する |
| Claude Code | SessionStart/SessionEnd、ツール実行等のフック、transcript_path | 会話ログは非同期更新で、通知時点では最新メッセージが未反映の場合がある |
| Codex | 開始・終了・ツール実行のフック、transcript_path | 会話ログ形式は安定したインターフェースではない。ローカル／クラウド等の実行環境で対応が異なる |

出典:

- [Cursor Hooks](https://prod.cursor.com/docs/hooks)
- [Claude Code Hooks](https://code.claude.com/docs/en/hooks)
- [Codex Hooks](https://learn.chatgpt.com/docs/hooks)

AIの1ターン終了と開発作業の終了は同じではない。
例えばCodexのSessionEndは、単に別の会話へ切り替えただけでは即時に発生しない。
異常終了・スリープ・ログの遅延もあるため、終了通知だけで収集の完全性を保証しない。

### AIによる生成・判定

- Cursorには非対話実行用CLIがあり、公式のCLI紹介ではサブスクリプションでの利用が案内されている。ローカル連携から呼ぶ候補。ただし配布する製品としての利用条件・現在の課金・利用枠は実装前に確認する。
- Claude Codeには `claude -p` がある。公式バイナリにユーザー自身がログインする方式と、独自アプリが契約認証を流用する方式は別。認証情報を収集して中継する設計にしない。製品組み込みの条件を満たすかは具体的な構成で確認する。
- Codexには組み込み用App Serverがある。またSign in with ChatGPTには、対象リクエストでユーザーのChatGPTプランを利用する経路がある。公開手順はOSS・ローカルホスト向けで、有料・リモートホストのアプリには別途申し込みが案内されている。プレビュー制限があり、既存のGoサーバーから無条件に利用できるという意味ではない。

出典:

- [Cursor CLI](https://cursor.com/blog/cli)
- [Cursor Headless CLI](https://cursor.com/docs/cli/headless)
- [Claude Code programmatic execution](https://code.claude.com/docs/en/headless)
- [Claude Code authentication and product integration conditions](https://code.claude.com/docs/en/legal-and-compliance)
- [Codex App Server](https://learn.chatgpt.com/docs/app-server)
- [Sign in with ChatGPT: plan usage](https://developers.openai.com/siwc/token-sharing-open-source)
- [Sign in with ChatGPT: preview limitations](https://developers.openai.com/siwc/token-sharing-open-source/preview-limitations)

### MCPによる教材取得・結果保存

3つのツールともMCP接続の仕組みを持つ。学習サービスが教材取得や生成結果保存のツールを提供する構成は可能。
これはAI側が学習サービスを呼ぶ経路であり、Webアプリから閉じたAIツールを起動する仕組みではない。

- [Cursor MCP](https://prod.cursor.com/docs/mcp)
- [Claude Code MCP](https://code.claude.com/docs/en/mcp)
- [Codex MCP](https://learn.chatgpt.com/docs/extend/mcp)

## 5. 構成案の比較（未採用）

| 案 | ユーザーの操作・特徴 | 負担・限界 |
|---|---|---|
| AIチャット＋MCP | 普段のAIに学習を依頼し、教材を取得・結果を保存する | これだけでは継続的な自動収集にならない |
| フック＋小さな収集スクリプト | 初回に設定し、イベント時に会話やGit差分を記録・送信する | イベント間の変更履歴や、AIツールを使わない編集を逐次記録するとは限らない |
| PC上の常駐連携プログラム | フックに加えて保存されたファイル変更も監視する。学習画面との橋渡しをする | インストール・配布・更新・OS対応が増える |

独立した画面を持つ収集専用アプリは必須ではない。
まずフックと小さなスクリプトで、会話と節目の差分を十分に取得できるか試す案を最後に提示した。
これも未決定であり、ユーザーは検討のために議論を中断している。

## 6. 使いやすさを優先した体験案（未採用）

1. 初回にAIツールと対象プロジェクトを連携する。
2. 普段どおり開発する。会話・変更を自動記録し、記録中表示と一時停止を用意する。
3. 終了候補を通知し、「学習を準備」の1クリックで対象範囲を確定する。
4. 対応するAI実行経路で候補・問題を生成する。
5. 学習アプリで問題に答え、AIによる判定・解説と履歴を見る。

終了時の1クリックは、AIの応答終了と開発完了の誤判定を避けるための提案。
自動終了や完全自動生成を捨てる決定ではない。
アプリ画面からの生成・判定には、MCPとは別にAIを実行する経路が必要。
実行経路が使えないときの待機・再開も設計する。

## 7. フェーズ3の既存設計で活かせるもの・見直すもの

[phase3-design.md](phase3-design.md)は、前提変更前の設計を含む草案として保持する。

### 活かせる考え方

- LearningCandidate: 学ぶ対象の候補。
- LearningSet: 選んだ候補についての2〜3問のまとまり。
- Question: セット内の個々の問題。
- AnswerAttempt: 1回分の回答と判定結果。答え直しの履歴を残す。
- 判定の通信失敗と、理解度の「判定保留」は別に扱う。
- 回答を先に保存し、判定だけの再試行で回答履歴を増やさない。
- 根拠は出典を辿るために持つ。場所だけ保存し、excerpt本文は重複保存せず表示時に教材から取得する。
- 生成物の構造・根拠の存在・所有者をサーバーで検証する。

### 再設計する部分

- GoサーバーがユーザーのOpenAI APIキーで生成・判定する前提。
- 生成POSTを受けたサーバーが直ちにAIを呼ぶAPI構成。
- OpenAIのみ／モデル固定と、ユーザーのAIツールを使う方針の整合。
- PRスナップショットを必須の親とするデータ構造。PRができる前の開発記録や、複数セッションとPRの関連付けが必要。
- AIジョブの実行場所、待機・重複防止・再試行・結果保存の責任分担。
- AIによる問題生成・判定中に接続が切れた場合の復旧。

以前提示したexcerptの4 KiB・根拠最大3件・合計12 KiBは採用していない。
教材入力と画面表示のサイズ制限は別途設計する。

## 8. 再開時に決めること・小さく検証すること

### 未決事項

- 会話と節目のGit差分で十分か、保存ごとの変更履歴まで必要か。
- 開始・終了をどこまで自動判定するか。
- 最初に対応するAIツールと実行環境。
- 初期設定をスクリプト／プラグイン／常駐プログラムのどれで配布するか。
- 学習はチャットかアプリ画面か。画面からAIへ実行依頼する場合の正式な接続経路。
- ローカル／OSSか、ホスト型サービスか、有料提供か。
- ローカルで記録する範囲とサーバーへ送る範囲。従来の公開PR限定との整合、秘密情報の除外。
- AIの契約利用枠がない・上限に達した・PCが停止した場合の扱い。

### 最初の検証案

1つのツール・1つのプロジェクトに限定して、以下を確認する。

1. 開始イベントと対象リポジトリを識別できる。
2. 会話とコード差分を途中・終了時に記録できる。
3. 重複通知、ログ書き込み遅延、中断・再開でも既存記録を壊さない。
4. ユーザーの正式な認証経路で問題を1件生成できる。
5. 生成結果を既存のGoサーバーへ保存して表示できる。
6. 回答を保存し、同じ経路で判定・解説を返せる。

この検証により、常駐アプリが本当に必要か、フック＋スクリプトで足りるかを判断する。
現時点では設計の検討メモを保存するまでとし、これらの実装は開始しない。
