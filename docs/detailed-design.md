# Learning Companion 設計概要（第二案・現行）

更新日: 2026-10-26
[要件](../requirements.md)を実現する責任分担。開発順は[第二案](implementation-plan-v2.md)、現在地は[現在の作業](current-work.md)。

## 構成

```text
ユーザー ↔ AIツール内の自作スキル
                 ↕ 本人認証付き接続（MCPを提案）
              Goサービス ↔ PostgreSQL / Object Storage
                 ↕
           React管理・閲覧画面
                 ↓
             復習・通知処理
```

スキルがAIへ学習手順を指示する。Goは学習記録・復習予定・通知を扱い、AI APIを呼ばない。
学習開始に公開PR・元教材のサーバー保存を要求しない。AIツールが手元のコード等を読み、アプリには送信内容を確認した問題・回答・フィードバック等を保存する。AIツールによる読み取りとサーバーへの送信は別の境界とする。
接続の実装方式は詳細設計で決める。Web Cookie、アプリ接続トークン、AI製品の認証は別物として扱う。

## 論理データ

| データ | 役割 |
|---|---|
| PRSnapshot / ConversationUpload | 任意に取り込む教材と会話。既存実装を維持し、学習記録の必須の親にしない |
| LearningCandidate / LearningSet | 候補と選択した学習対象。候補の保存範囲は未決。PRとの関連は任意 |
| LearningSession / Question | 初回・復習の回と、その回の問題 |
| AnswerAttempt / Evaluation | 提出内容と判定・解説。ヒント・自己評価・テスト結果を区別 |
| LearningNote | ユーザーが保存した要点・未解決点 |
| ReviewSchedule / Notification | 次の復習と通知の管理 |

これは論理上の役割。テーブル分割、型、API、状態enumは未確定。復習問題を初回へ上書きしない関係を詳細設計で定める。

## 共通ルール

- 認証済みユーザーから所有者を決め、関連データも同じ所有者であることを検証する。
- 保存済み教材を参照する場合は所有者・対象・範囲を検証し、内部Storageキーを外部指定させない。参照は任意で、元教材未保存の学習も受け付ける。
- 保存済み教材の根拠は場所で保持する。手元の出典は原文を保持した証明にしない。問題用コードと引用元は区別する。
- 問題・回答・フィードバックに含まれるコード等も送信対象。保存前にユーザーが内容を確認・除外できるようにし、一般化した内容と実際の提出内容を混同しない。確認方法・保存単位は詳細設計で決める。
- 再開・復習は保存済み学習記録を基本とし、足りない元コードや会話は本人に再提示を依頼する。
- 問題作成から回答・判定・フィードバックまではAIエージェント上で進める。学習中は保存処理を実行せず、学習後の保存段階で初めて実行する。サーバーは送信された記録の構造・関連・所有者を検証する。
- 学習中に保存状態を通知しない。保存エラーは実際の保存操作に対する結果としてのみ扱う。保存済み記録は保持し、未保存内容の永続保持や別チャットでの復元は保証しない。
- 保存要求は冪等に扱い、同一IDで異なる内容が来た場合は競合として扱う。
- AIの評価は能力認定ではない。処理失敗と理解度の判定保留を分ける。
- サーバーが直接観測できないAI側の失敗を、確定したサーバー状態として推測しない。未提出・待機・再送の扱いを契約で決める。
