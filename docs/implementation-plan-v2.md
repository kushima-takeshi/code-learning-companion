# Learning Companion 開発計画・第二案

作成日: 2026-10-26
状態: 現行作業計画（2026-10-26に公開PR必須の前提を撤回）。手元のコード等で学び、確認した学習記録を保存する方針を採用。第二案の実装は未着手。本文の接続方式・通知方法・復習数値等の提案は未確定。
文書の読み方は[文書案内](README.md)、未決事項と次の一手は[現在の作業](current-work.md)を参照。
対象: このリポジトリのLearning Companionと、接続する自作の学習スキル。

## 1. 目的

AIの補助で開発したコードを「動くが自分では説明・修正できない」状態で終わらせず、出題・回答・解説・後日の復習によって理解を確かめる。

学習はユーザーが普段利用しているAIツール内で行う。
公開PRの作成・プッシュ・取り込みや元教材のアプリ保存を、学習の必須条件にしない。
Learning Companionは送信内容を確認した問題・回答・フィードバック等の学習記録を保存し、学習履歴の閲覧、復習予定、通知、別チャットでの再開を担当する。

ステアログ、書籍・記事の学習、統合プロフィール、ステアログウェブとの連携は今回の開発範囲に含めない。

## 2. 第一案から変更すること

| 項目 | 第一案 | 第二案 |
|---|---|---|
| 学習する場所 | Reactの問題回答画面 | ユーザーのAIツールのチャット・練習ファイル |
| 問題生成・自由記述判定・解説 | GoサーバーからOpenAI APIを呼ぶ | スキルの指示に沿ってユーザーのAIが実行 |
| AI認証 | アプリにOpenAI APIキーを入力 | AIツール側の既存認証を使用。アプリはAI認証情報を預からない |
| アプリ画面 | 出題・回答・AIとの対話 | 学習履歴・回答・フィードバックの閲覧、復習一覧、接続・通知設定。PR取り込みは任意 |
| 深掘り | アプリ独自のチャット | AIツール内で会話し、ユーザーが選んだ学習要点を保存 |
| 復習問題生成 | アプリからAIを呼ぶ | ユーザーがスキルで復習を開始してから生成 |
| 教材の入口・収集 | 公開PRを取り込み、アプリで出題 | AIツールが手元のコード・差分・許可された会話を読む。元コードや会話全文は自動収集せず、公開PR取り込みは任意 |

この計画では、GoからAI製品のサブスクリプションを代理利用する仕組みは作らない。
ユーザーのAIツールでスキルが動くことを前提とし、利用枠・対応モデル・権限はそのツールに従う。

## 3. 最初に実現する体験

1. ユーザーが手元のコード・未コミット差分・許可された会話で学習を依頼する。PRの作成・公開・取り込みは不要。
2. AIツールにスキルと接続設定を導入し、Learning Companionの本人アカウントと紐付ける。
3. AIツールで「今の変更について学習したい」と依頼する。スキルは指定範囲を読み、必要なら本人の保存済み学習記録を取得する。
4. AIツールで読む範囲とアプリへ送信する範囲を分ける。元コードや会話全文は自動送信せず、過去の全チャットを自動で読めるとは扱わない。
5. AIが最大3件の候補と選定理由・根拠を提示し、ユーザーが1件選ぶ。
6. 選んだ候補の問題を2〜3問作り、AIエージェント上で1問ずつ出題する。学習中にアプリへの保存処理は実行しない。
7. ユーザーが文章・選択肢・コードで回答する。コードは本番ファイルと別の練習用ディレクトリに書く。
8. AIエージェント上で判定・フィードバックまで進める。学習中は保存処理・保存状態の通知を行わない。学習後、ユーザーが保存する段階で送信内容を確認し、選んだ記録を保存する。
9. アプリで履歴と次回復習日を確認する。
10. 復習通知を受け、対応チャットでスキルを起動する。保存済みの問題・回答・フィードバックから復習・未完了学習を再開する。元コード等が必要なら本人が再提示する。

通知を受けた時点で問題を事前生成する必要はない。
アプリから閉じたAIツールを自動起動する機能は初期対象外とする。

## 4. 構成と責任分担

```text
ユーザー ↔ AIツール内の自作スキル
                  ↕ 認証付きMCPツール
             Goの学習サービス
              ↙           ↘
     PostgreSQL        Object Storage
              ↖           ↗
             Reactの管理・閲覧画面
                    ↓
             復習予定・通知処理
```

### スキル

- 手元の教材の読み取り、候補選択、出題、回答待ち、解説、送信内容の確認、保存確認、再開の手順を定義する。
- 問題・回答・フィードバックに混ざる非公開情報も確認対象とし、除外・一般化または保存中止できるようにする。具体的な確認単位は順序1で決める。
- 最初はCodexで検証する案とする。Claude Code・Cursorは共通契約が安定してから追加する。
- 既存スキルは比較対象とし、今回は自分の学習体験に合わせたスキルを作る。既存文章やコードの流用は前提にしない。
- 回答前に解答を書かず、コード記述ではユーザーの完了申告を待つ。
- ヒントの有無と本人の自己評価を記録する。エディターの補完を完全に制御できるとは扱わない。

### MCP接続とGoサーバー

- MCPはAIから学習記録の保存・取得処理を呼ぶ窓口として提案する。AIモデルの代わりに問題を考えない。
- 初期はローカルの薄いMCPアダプターから認証付きGo APIを呼ぶ案とする。ブラウザ向けCookieを流用しない。
- Web画面で発行・失効できる期限付きの連携トークンを用意し、サーバーにはハッシュだけを保存する。学習データの読み書きに権限を限定する。
- トークンは接続側の設定で扱い、スキル本文やモデルに渡す教材へ埋め込まない。
- リモートMCPやOAuthの配布方式は、複数ツールへの展開時に再検討する。第一段階で全方式を実装しない。
- 保存・所有者確認・参照検証・二重送信対策・復習予定の計算はサーバーで保証する。

### React画面

- 学習履歴、問題・回答とフィードバック、次回復習日を表示する。公開PR取り込みは任意の教材入力とする。
- AIツールとの接続解除、復習の終了・再開、通知設定、データ削除を提供する。
- 再開時は対象IDを含む短い依頼文をコピーできるようにする。特定ツールへの自動起動に依存しない。

進捗チェックが完了でも、所有者・公開状態・スナップショット整合性などの懸念を解消済みとみなさない。

## 6. 保存する情報と状態の方針

### 主なデータ

- LearningCandidate: タイトル、説明、選定理由、根拠。提示はスキル内で行い、アプリ保存の範囲は未決。
- LearningSet: 選択した学習テーマと初回学習のまとまり。PR ID・保存済み教材IDを必須にしない。
- LearningSession: 初回・復習の区別、開始・完了状態、対応する問題群。復習で初回の問題を上書きしない。
- Question: 出題文、種別、順序、練習コード、正解・期待要点、根拠。
- AnswerAttempt: 提出した回答・コードの内容、ヒントの有無、任意の苦手理由・自己評価、日時。
- Evaluation: 回答に対する理解度、できた点・不足点・解説・根拠。実行したテスト結果とAIの判断を区別する。
- LearningNote: 保存を選んだ要点・未解決点。
- ReviewSchedule / Notification: 復習段階、予定日、停止状態、通知・送信結果。

コード回答を保存する場合は、送信内容を確認した提出時点の本文を保存する。ローカルのファイルパスだけでは本文を保存したことにしない。
元コード・差分・会話全文は必須保存項目にしない。学習記録から除外・一般化した内容を、元の提出内容そのものとして扱わない。整合性・保存単位の詳細は順序1で決める。
モデル名・ツール名・スキル版は分かる範囲で記録し、不明なら未設定とする。

### 保存と再開

- 学習中は保存処理を実行しない。学習後、ユーザーが保存する段階で選んだ記録を送信する。保存対象の単位、候補の保存範囲は詳細設計で決める。
- 実際の保存操作が失敗した場合だけ、保存エラーを伝えて再送できるようにする。保存済みの回答は判定・保存失敗で消さない。回答修正は別履歴、判定再送は同じ回答へ対応付ける。
- 保存操作にリクエストIDを付け、再送でデータや復習予定を重複作成しない。同じIDで異なる内容は拒否する。
- チャットを閉じた場合、アプリから再開できるのは保存済みの記録・進捗に限る。未保存内容の永続保持や復元は保証しない。
- 再開では保存済み学習記録を取得する。保存していない元コードや会話は復元できないため、必要な場合は本人に再提示を依頼する。

### 根拠と評価

- スキルは読んだコード・差分・会話に基づき理由を示す。根拠の原文をアプリへ先に保存することは要求しない。
- 保存済み教材への根拠参照は任意。使用する場合は所有者・存在・範囲を検証し、excerpt本文を重複保存しない。
- 手元のパス・行番号等の任意の出典情報は、サーバーが原文を保持・検証した証明にしない。形式と保存範囲は詳細設計で決める。
- AIが作った要約と原文は区別する。原文未保存でも記録を受け付け、説明の意味的な正しさを保証したとは扱わない。
- 選択肢を含む回答の判定・解説はユーザーのAIエージェント上で行う。サーバーは学習記録の検証・保存を担当する。
- AIの評価と本人の自己評価、ヒントなし／あり、テスト結果を分ける。能力認定や言語習得率への変換は今回行わない。

## 7. 開発順序

工数・日付は、接続試作後に見積もる。各段階を小さな変更に分け、ユーザーが実装し、提案コードと理由をレビューする進め方を維持する。

| 順序 | 作業 | 完了条件 |
|---|---|---|
| 1 | 保存項目・送信前確認・接続・認証・状態の契約を定める | PRなしの正常系、保存範囲、除外・一般化、保存失敗・再開の扱いを説明できる |
| 2 | スキルと接続の最小試作 | PR・元教材の保存なしで、1つのAIツールから本人認証し、確認済みの固定形式の学習記録1件を保存・取得できる。別ユーザーは拒否される |
| 3 | 手元の教材で学習する手順と保存範囲の確認 | 指定したコード・差分・会話から学習でき、元教材を送らず、問題・回答・フィードバックの送信範囲を確認・除外できる。PRは任意 |
| 4 | 学習候補と問題セットの生成手順・保存 | 最大3候補から1件選び、AIエージェント上で2〜3問を順に出題できる。学習中に保存処理を実行しない |
| 5 | 回答・判定・解説・コード問題 | ユーザーが実装して回答し、判定まで保存できる。学習後の保存段階で選んだ記録を保存し、保存エラー時には再送できる |
| 6 | 履歴一覧・詳細・途中再開 | アプリで保存した問題・回答・フィードバックを確認し、別チャットで再開できる。不足する元コード等は再提示を依頼できる |
| 7 | 復習スケジュール・再出題 | アプリが予定を決め、スキルが期限到来の学習を取得し、保存済み学習記録から別の問いを作る。元教材が必要なら再提示を依頼し、初回履歴を残す |
| 8 | 復習通知 | アプリ内の期限表示に加え、希望者へメールで復習を案内する。通知はAIを起動しない |
| 9 | 削除・上限・公開前検証 | 本人データの削除、接続失効、容量・頻度制限、再送・通知失敗を含む一連の確認が通る |

順序2では最小の保存・取得画面または応答確認まで作り、形式の固定データで接続を確かめる。
以降の機能を固定データで完成扱いにしない。実際のAI出題と人間の回答を順序4〜6で評価する。
認証と所有者確認は初期から行い、公開前の段階まで先送りしない。

### 最初の小さな完成形（順序6まで）

手元の開発内容1件を使い、公開PRや元教材のアプリ保存なしで、候補選択、コード問題を含む回答、判定・解説、送信前確認、保存、アプリ閲覧、別チャット再開までを通す。
この段階で実際に学習し、問題が本人のつまずきを拾うか、保存と再開が負担にならないか確かめる。
復習と通知の実装前に、出題体験を一度評価する。

## 8. 復習・通知の提案ルール

- 旧仕様の3日・14日・30日を出発点とするが、日付の基準を曖昧にしない。
- 提案: 初回完了から3日後に初回復習。成功後は実際の復習日から11日後、次の成功後は16日後を目安にする。予定どおりなら初回から3・14・30日になる。
- セット内に「もう一度」があれば翌日、「一部できた」があれば3日後に同段階を再試行する。全問「できた」の場合だけ次段階へ進む案とする。
- 「判定保留」や判定待ちは段階を進めず、未完了として再開できるようにする。初回の「学習完了」と「復習段階の成功」は別である。
- 最終段階の成功は「復習計画完了」と表示する。能力の保証と誤認される「言語習得済み」にはしない。
- 復習終了は履歴を残して通知・予定を停止する。再開時は新しい予定を作る。
- 最初のアプリ外通知は、同意・宛先確認済みメールへの1日1回のまとめ通知を提案する。タイムゾーン・通知時刻・停止方法を設定できるようにする。
- 送信記録と重複防止、失敗時の再試行を実装する。メールの到達自体は保証しない。復習停止・削除後は送信しない。
- メールサービス・送信元設定は順序8までに決める。GitHubにメールアドレスがある前提にしない。

これらは未確定の提案値。仕様04にも未決として記録し、具体ルールをレビューして確定後に実装する。

## 9. 範囲と後続機能

### 初期リリースに含める

- 公開PRなしで、手元のコード・差分・許可された会話から学習する入口。既存の公開PR取り込みは任意として残す。
- 1つのAIツール向け自作スキルと、認証付きの取得・保存連携。
- 候補選択、問題、回答、コード実践、判定・解説。確認した問題・回答・フィードバックと選択した学習要点の保存。
- 学習履歴一覧・詳細表示、別チャット再開、復習予定と通知。保存済み教材への根拠表示は任意連携として扱う。
- 所有者分離、接続失効、削除、保存容量・取得頻度の制限。

### 初期リリース後に検討

- Claude Code・Cursor等への展開と配布方法の整備。
- 任意の公開PR教材連携の拡充（本文読み出し・根拠参照・会話関連付け）、指定リポジトリのPR自動取得。最小接続の必須条件にしない。
- 会話取得を簡単にする各ツールのフック等。全履歴の自動取得・常駐監視は必要性が確認できた場合のみ。
- 他人のPRを探して学ぶための推薦・探索機能。既存の公開PR取り込みは引き続き利用可能。
- アプリ画面だけでの問題回答・AI呼び出し、モバイルでの学習。

ステアログ等の他プロジェクトとの連携は本計画では設計・実装しない。

## 10. 検証と公開条件

### 自動で確認すること

- 取得・保存・再開・削除・MCPの各経路で所有者が分離されている。
- 無効・期限切れ・失効済みの接続トークンでは操作できない。
- PR ID・保存済み教材IDなしの学習記録の保存・再取得、不正な構造の保存拒否。
- 任意の保存済み教材参照を実装する場合は、根拠の存在・行範囲・教材との対応を検証する。
- 同じ保存要求の再送、判定再送、復習完了の重複処理で履歴が増殖しない。
- 保存失敗・再送、モデル変更、別チャット再開で保存済み履歴が壊れない。
- 日時を制御して復習予定と通知を検証する。実時間の数週間待ちを必要としない。
- 削除後にDB・Storage・通知キュー経由で内容が残って利用されない。外部チャットや端末へ既に渡した内容はアプリから消せない旨を明示する。

### 実際に人が確認すること

- 公開PR・元教材のアプリ保存なしで、スキルが候補の理由を示し、選択を待つ。
- 問題・回答・フィードバックの送信内容を確認・除外でき、元コードや会話全文が自動送信されない。
- コード問題でAIが先に解答せず、本人が練習ファイルで回答できる。
- 解説が提出した回答と根拠に対応している。
- 学習中に保存処理・保存状態の通知が発生しない。学習後の保存操作で失敗したときは「保存済み」と案内しない。
- 初回チャットを閉じても、次のチャットで再開できる。
- 通知からどの学習を再開するか迷わない。

生成結果の品質はスキルの指示だけで保証しない。固定応答による接続テストと、人間による実際の学習を分けて評価する。
旧仕様の「サーバー側LLM呼び出し数制限」は直接適用しない。サーバーは教材取得・保存・容量・通知の上限を管理し、外部AIの利用回数全体を制御できるとは扱わない。

## 11. 各実装の前にレビューする項目

1. 学習をAIツール内、アプリを記録・復習・通知に集中させる方針。
2. 最初の対応先をCodexとし、1つずつ展開する順序。
3. ローカルMCPアダプターと期限付き連携トークンによる最初の接続案。
4. 元コード・会話全文を自動収集せず、問題・回答・フィードバックの送信内容を確認する方法と除外・一般化の扱い。
5. 復習の具体的な日付ルールとメール通知。

requirements.mdとspec 03〜06は現行方針へ更新済み。phase3-design.md、第一案・調査メモは履歴として残す。
